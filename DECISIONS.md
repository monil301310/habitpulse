# DECISIONS

Ambiguities in the spec resolved for HabitPulse V1. Newest entries at the top of
each phase section. The spec says: pick the simplest option that fits, and log it
here.

## Phase 8 — Final QA and packaging

1. **Export formats:** JSON is the complete backup (habits, reminders, logs,
   settings, counts, schema version); CSV is one row per logged day with the
   habit name resolved. Both are generated by a pure `ExportBuilder` so escaping
   and ordering are unit-tested.
2. **Export destinations:** Windows writes to Downloads and reveals the file in
   Explorer; Android writes to app documents and opens the system share sheet.
   No export is uploaded anywhere.
3. **Release signing key lives outside the repo.** `android/key.properties` is
   gitignored and points at `C:\Users\monil\habitpulse-keys`; the Gradle script
   falls back to debug signing when the file is absent, so a fresh clone still
   builds.
4. **Android ships a universal APK for sideloading and an AAB for Play.** Version
   is `1.0.0+1`.
5. **MSIX is self-signed** with the `msix` package's test certificate. That is
   fine for local installation after trusting the cert, but store/distribution
   builds need a real code-signing certificate.
6. **Local Maven seeding was a build-environment fix, not a product change.**
   The release engine artifacts were copied into `~/.m2` and `mavenLocal()` is
   listed first; normal machines still download from Google/Maven Central.
7. **Privacy policy is committed** (`PRIVACY.md`) and linked from the README and
   Settings → About; it describes local-only mode, optional Supabase, Google
   sign-in and deletion.
8. **GitHub publication is a separate hand-off step.** Secrets/builds are
   ignored before the first commit; the remote/auth details come from the user.

## Phase 7 — Polish and responsive layouts

1. **Breakpoints:** bottom navigation below **720 dp**, navigation rail from
   720 dp, extended rail from **1180 dp**, and the Today list/detail two-pane
   from **900 dp**. 900 keeps the 800 dp widget-test surface on the single-pane
   layout (which overflowed at 700) and matches small tablets.
2. **Tabs, not pushes.** Today, Insights and Settings live in an `IndexedStack`
   driven by a `Notifier<int>`, so tab state and scroll positions survive
   switching and the rail/bottom bar can stay visible.
3. **Embedded detail reuses the existing screen.** `HabitDetailScreen(embedded:
   true)` keeps its own `Scaffold`/app bar but hides the back arrow and adds a
   close button; the two-pane shell only supplies the width. This avoided
   splitting the 780-line detail screen into body/header fragments.
4. **Selection lives in the shell.** Tapping a card calls `onOpenHabit` instead
   of pushing a route when the pane is wide; the selected card gets a primary
   outline. On narrow layouts the same callback is absent and the screen pushes
   as before.
5. **Global shortcuts** use `CallbackShortcuts` above the shell: `Ctrl+N`,
   `Ctrl+1/2/3`, `Ctrl+,` and `Esc`. `Esc` pops the top route if there is one,
   otherwise returns to Today.
6. **Windows window/tray** use `window_manager` + `tray_manager` +
   `shared_preferences`. The window restores its last size and position and has a
   460×620 minimum. Closing hides to the tray **only when the tray was created
   successfully**; otherwise the close proceeds normally so the app cannot become
   unreachable.
7. **Tray menu** is the legacy `tray_manager` bridge (Show / Hide / Quit). It is
   marked deprecated upstream; the bridge is isolated in `windows_shell.dart`
   with a file-level ignore so moving to the native API later is a one-file
   change.
8. **Start with Windows** uses `launch_at_startup` and is shown only when
   `WindowsShell.isActive` is true, so widget tests and Android never touch the
   Windows-only plugins.
9. **Tray icon** is a copy of the Windows app icon (`assets/app_icon.ico`) loaded
   through the plugin's asset support, so it works in debug and release.
10. **Motion respects accessibility:** the tab/list and detail fades collapse to
    zero duration when `MediaQuery.disableAnimations` is set.

## Phase 6 — Android widgets

1. **`home_widget` + native RemoteViews.** The widgets are real Android
   `AppWidgetProvider`s; Flutter pushes JSON and a rendered image into the
   plugin's shared preferences. This keeps the widget process independent of the
   Flutter UI and lets row taps run while the app is closed.
2. **The heatmap widget is a rendered image.** RemoteViews cannot draw the
   contribution grid, so `renderFlutterWidget` renders the same card (icon,
   name, streak, 24-week grid, today state) to `heatmap_image.png` and the native
   widget shows it in an `ImageView`. The card follows the system light/dark
   appearance.
3. **One habit per heatmap widget for V1.** It shows the first active habit;
   tapping opens that habit. Per-widget habit selection needs a configuration
   activity and is a deliberate follow-up.
4. **Checklist caps at six rows.** A `+N more` line covers the rest; RemoteViews
   list adapters would be the next step but are unnecessary for a typical day.
5. **Tapping a checklist row toggles done ↔ cleared** via the plugin's
   background isolate. It uses its own Drift connection, then rewrites the
   checklist JSON and updates the widget. All of it is wrapped in error guards so
   a failure cannot crash the app.
6. **Background writes are reconciled on resume.** Because widget taps use a
   second SQLite connection, Drift streams in the open app would not see them;
   `WidgetSync` invalidates the habit/log/reminder/settings providers on resume.
7. **Refresh schedule:** app start, 2 seconds after any local change, on resume,
   and every 15 minutes. `updatePeriodMillis` is `0` so Android does not wake the
   app on its own schedule.
8. **Theme-aware resources.** Widget colours live in `values` and
   `values-night`; no hard-coded colours in the Kotlin providers.
9. **Widget taps use deep-link URIs** (`habitpulse://habit?habitId=…`,
   `habitpulse://today`) handled by `HomeWidgetLaunchIntent`; the app routes them
   through the shared navigator key.

## Phase 5 — Accounts and sync

1. **Cloud is optional.** Without `SUPABASE_URL` / `SUPABASE_ANON_KEY` in `.env`,
   `CloudRuntime` stays unconfigured and the app makes no network calls; every
   feature continues to work locally. This lets the app be used before the
   Supabase project exists and keeps widget tests hermetic.
2. **Pull before push.** Every table pulls rows newer than its `last_pull`, then
   pushes local rows newer than `last_push`. Pulling first means a newer remote
   row is applied locally before the local row is uploaded, so "newest
   `updated_at` wins" holds on both sides instead of a stale push clobbering a
   fresh remote edit.
3. **High-water marks per table** live in a new local `sync_state` table
   (`table_key`, `last_push`, `last_pull`), schema v4. Pull uses `gte` so a row
   written at the same timestamp is re-applied (idempotent) rather than missed.
4. **Log conflicts:** inside a 5-second window `done` beats `missed`/`partial`;
   a local `done` is never replaced by a remote non-done status. Outside the
   window the newest timestamp wins. Same-day logs created on two devices with
   different ids are merged by `(habit_id, date)`; the loser is soft-deleted
   locally **without** changing its `updated_at`, so the deletion is not pushed
   and cannot erase the winner on another device.
5. **Settings ownership.** The local settings row stays under the literal
   `local` user id; on push it is written with the authenticated `user_id`, and
   on pull remote settings are folded back into that local row. This avoids two
   settings rows after sign-in.
6. **Session security.** The Supabase session is persisted through
   `flutter_secure_storage` (Android Keystore / Windows Credential Manager),
   not shared preferences.
7. **Sign-out clears local data** after a confirmation dialog, cancels scheduled
   notifications and resets the sync high-water marks. Cloud rows stay in the
   account.
8. **Sync triggers:** app start, 2 seconds after any local data change
   (debounced), on connectivity restored, every 15 minutes in the foreground,
   and on Supabase Realtime events for all four tables.
9. **Magic-link redirect** is `io.supabase.habitpulse://login-callback`, declared
   as an Android intent filter. Windows magic links open in a browser and cannot
   return the session to an unpackaged desktop app yet, so **email + password is
   the recommended Windows path**.
10. **Sign-in lives in Settings** instead of blocking the first launch. The
    spec's one-time intro can be enabled once keys are configured; blocking the
    app would break the local-first experience for users who never sign in.
11. **Remote ids stay text UUIDs** generated on the device; `user_id` is a
    `uuid` with a `default auth.uid()` and RLS policies restrict every operation
    to the owner. The service-role key is never used client-side.
12. **Realtime is additive.** If Realtime is unavailable, the debounced,
    reconnect and 15-minute triggers still converge; realtime only makes the
    common case near-instant.

## Phase 4 — Reminders

1. **Notifications are local and offline** via `flutter_local_notifications`
   22.3.3 on Android, Windows and the desktop platforms it supports. Time zones
   come from `flutter_timezone` + the `timezone` package, so DST and travel do
   not shift reminder times.
2. **Scheduling strategy.** On every data change (habits, reminders, logs,
   settings), the app cancels the previous schedule and re-creates the next
   **7 days** of reminders, capped at 180 notifications. A completed day is
   therefore never reminded again, and a reminder added in the app is picked up
   within ~2 seconds.
3. **Reminder days.** An empty weekday set on a reminder means "follow the
   habit's schedule"; choosing days intersects with the habit's due days.
   Reminders only fire on days the habit is due and not already done.
4. **Quiet hours** suppress *all* notifications (reminders, recheck and morning
   recheck) whose time falls inside the window. Default 23:00–07:00, wrapping
   past midnight.
5. **Recheck content.** The daily recheck is scheduled at the configured time
   only if at least one due habit is still open that day. For future days the
   body is generic because the future state is unknown; the in-app checklist
   always computes the live list. The optional morning recheck does the same for
   the previous day.
6. **Action buttons.** Done, Skip and the type-specific action (Avoided /
   Slipped / +1) plus 10-minute and 1-hour snooze. Android executes these in a
   background isolate that opens the Drift database directly, so they work with
   the app closed. **"Later today" snooze is not a separate button**; the 1-hour
   option and the daily recheck cover that case. Windows toast buttons activate
   the app (Windows requires foreground activation for unpackaged apps) and the
   action is applied on launch.
7. **Schema v3** adds `settings.notification_sound`. Quiet hours, recheck times
   and sound now persist in the `settings` table; the theme is still in-memory
   and will move there with the full settings work.
8. **Android platform setup.** `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`,
   `RECEIVE_BOOT_COMPLETED`, `VIBRATE`, `WAKE_LOCK`, core-library desugaring, and
   the plugin's `ScheduledNotificationBootReceiver` for `BOOT_COMPLETED` /
   `MY_PACKAGE_REPLACED`. Exact scheduling falls back to inexact if the exact
   alarm permission is missing.
9. **First-run setup.** A "Notification setup" screen guides permissions, exact
   alarms, the Samsung One UI battery steps and a test reminder. It is linked
   from Settings rather than blocking the first launch, to avoid nagging.
10. **Verification limits.** The headless emulator rendered notifications with
    their action buttons and registered exact alarms, but did not deliver taps
    to the notification action row, so the final "tap Done while closed" check
    must be done on the real Galaxy S21 Ultra (or the Windows desktop).
11. **Windows limitations.** Unpackaged apps cannot cancel or enumerate toasts
    (the plugin documents this), so rescheduling mostly adds new scheduled
    toasts and old ones expire naturally. MSIX packaging is Phase 8 work.
12. **Required Android receivers.** `flutter_local_notifications` 22 does not
    declare its own receivers, so the app manifest must declare
    `ScheduledNotificationReceiver` (scheduled delivery) and
    `ActionBroadcastReceiver` (action buttons), in addition to the boot receiver.
    Their absence was the cause of "notification fires but nothing happens".
13. **Foreground vs background action writes.** Background actions (app closed)
    open a dedicated Drift connection so they work without the app. Foreground
    actions (Windows toasts, or Android while the app is open) go through the
    app's Riverpod providers and therefore its existing connection, so the UI
    updates immediately.

## Phase 3 — Heatmap and insights

1. **Heatmap orientation is fixed Monday-first.** Columns are Monday-started
   weeks and rows are M T W T F S S, as section 4 explicitly specifies. The
   `week_start` setting still controls which days form a week for X-per-week
   streaks, but does not rotate the heatmap.
2. **Shade rules.** Done = the habit's accent at full strength; partial = accent
   at 40–45%; skipped = a faint accent tint (12–14%); missed = neutral grey
   (8–11%); not due / future / open today = a faint neutral (3.5–4.5%). Today's
   square gets an on-surface outline. These are lightness steps, so they remain
   readable for colour-blind users.
3. **X-per-week unlogged days are neutral**, not missed, because those habits
   only need a weekly quota. Days logged as done still show as done.
4. **Scroll range.** A home card shows the most recent 30 weeks; the detail
   heatmap can show up to 156 weeks (~3 years) and auto-scrolls to today. The
   user can scroll back through the whole history (verified with 3 years of
   seeded data).
5. **Notes belong to a log.** A note can only be saved once the day has a log;
   the day sheet watches the log stream, so status/value edits update live and
   then enable the note. Days with a note draw a tiny dot on their square.
6. **"Synced" footer.** Until cloud sync exists (Phase 5), the card footer reads
   `Local · <time>` using the latest habit/log update timestamp, so it never
   claims a sync that did not happen.
7. **Insights defaults.** Completion rates exclude an open today (as in Phase 2).
   Best weekday is computed over all closed history (ties go to the earliest
   weekday). The monthly trend covers 6 months. Best/worst habits require at
   least 3 closed due days to avoid ranking on noise.
8. **Demo data is debug-only** (`kDebugMode`) and deterministic. Rows use a
   `demo-` id prefix so "Delete demo data" cannot touch real habits.
9. **Insights access** is a top-bar icon for now. The phone bottom navigation and
   the tablet/Windows two-pane layouts from section 6 are Phase 7 work.

## Phase 2 — Core habits

1. **Calendar dates are a value type, not `DateTime`.** `LocalDay` (year/month/day)
   models log dates and habit start dates. Arithmetic uses UTC internally so
   daylight-saving changes can never skip or duplicate a day. This keeps the
   domain layer free of Flutter and of time-zone bugs.
2. **Rollover is applied when "today" is resolved.** With the default 03:00
   rollover, 01:30 still belongs to the previous day. `effectiveTodayProvider`
   resolves it once per app launch; an automatic refresh at the rollover instant
   is deferred to the notification work in Phase 4.
3. **Streak rules as implemented:**
   - A completed due day extends the streak.
   - A skipped day and a not-due weekday are neutral.
   - A missed, slipped or partial day in the past breaks the streak.
   - Today never breaks the streak while it is open (no log, or a partial count),
     but an explicit "missed" or "slipped" today does break it.
   - Times-per-week habits count consecutive satisfied weeks; the in-progress
     current week cannot break the streak.
4. **Completion-rate denominator** = due days that have closed, plus today only
   when it is already done. Days that are not due are excluded, and skipped days
   count as due-but-not-completed. This avoids an in-progress day lowering the
   rate.
5. **One active log per habit per day.** Enforced by a partial unique index on
   `logs(habit_id, date) WHERE deleted_at IS NULL`. Soft-deleted logs are
   excluded, so a cleared day can be logged again. Schema bumped to **v2**; the
   `onUpgrade` first soft-deletes any pre-existing duplicates, then creates the
   index.
6. **Logging lives in one service.** `HabitLogService` is the only writer of
   `logs` rows. Notification actions, widgets and integrations in later phases
   will call the same methods, matching the "one service" groundwork in
   section 10.
7. **Count/timed "Done" sets the full target** (matching the notification
   behaviour in the spec); "+1" and "Log" update the value and derive
   done/partial from the target.
8. **Negative habits** are confirmed with "Avoided" (done) and can record
   "Slipped". They never complete automatically.
9. **Archive vs delete.** Archive sets `archived_at` and hides the habit while
   keeping history. Delete soft-deletes the habit plus its logs and reminders,
   after a confirmation dialog.
10. **Habit creation defaults.** New habits start today, get `sortOrder = 0`, and
    are ordered on the home screen by (due today first, sortOrder, createdAt).
    The form always sets a start date; "optional" is preserved in the data model
    as a nullable field.
11. **Reminder fields are in the schema and form placeholder, but the reminder
    UI is deferred to Phase 4.**

## Phase 1 — Foundation

1. **Flutter organisation / package id.** Project created as `habitpulse` with
   `--org com.habitpulse`, giving an Android application id of
   `com.habitpulse.habitpulse`. Chosen because it is a stable, reverse-DNS id
   and is trivial to change before release.
2. **Platforms generated.** `android` and `windows` only. iOS/macOS folders are
   omitted for now but nothing in the Dart code is platform-specific outside the
   `platform/` bridges, so they can be added with `flutter create --platforms`.
3. **Local database.** `drift_flutter`'s `driftDatabase(name: 'habitpulse')`,
   stored as `habitpulse.sqlite` in the OS application-documents directory. This
   keeps one code path for Android and Windows.
4. **SQLite delivery.** The installed `sqlite3` package uses Dart build hooks
   (native assets) to compile/bundle SQLite, which is why
   `sqlite3_flutter_libs` resolves to an EOL marker version. No extra manual
   setup is required; the build hook does it.
5. **Local calendar days.** `logs.date` and `habits.start_date` are stored as
   `yyyy-MM-dd` text, not timestamps, so a day never shifts across time zones
   (spec section 8). All other timestamps (`created_at`, `updated_at`,
   `deleted_at`, `archived_at`) are UTC `DateTime` columns.
6. **Schedule days** are stored as a comma-separated ISO weekday list
   (`1,3,5`, Monday = 1) in a single text column. Simple, readable in SQLite,
   and easy to serialise for sync later.
7. **Single local user.** Until accounts exist (Phase 5), `user_id` defaults to
   the literal `local`. The column is already present so the sync shape is
   stable.
8. **Soft deletes.** Every table has `deleted_at`; queries filter it out. Purging
   after 90 days is a Phase 5 concern.
9. **Riverpod style.** Hand-written `NotifierProvider` / `Provider` /
   `StreamProvider` instead of `riverpod_generator` codegen. Fewer moving parts
   for the foundation; codegen can be adopted later without changing call sites.
10. **Theme default.** Dark, with Light and System selectable. The selected mode
    is in-memory for Phase 1; persisting it to the `settings` table arrives with
    the full settings screen.
11. **Habit icons.** Phase 1 stored an icon *key* string and rendered a bolt
    placeholder. Phase 2 added the curated built-in icon set and picker.
12. **No seed data.** The database starts empty so a fresh install shows the
    empty home screen.
13. **Windows Visual Studio.** `flutter doctor` reports the machine's Visual
    Studio as "incomplete" (`isComplete: 0`) after a half-applied 18.9 → 18.10
    update. This is an environment issue, not a code issue. Repairing it in the
    Visual Studio Installer is a one-time setup step (documented in
    PROGRESS.md); Android development is unaffected.
